## 1. 감사 방법

- **드라이버**: Playwright(시스템 Chrome, `deviceScaleFactor:2`)로 랜딩→허브→워룸→킥오프→입장→경기(3D/2D)→감독타임→브레이크→하프타임→후반→종료→기자회견→신문 전 구간을 자동 주행. `setTimeout` 워프(6~20배)로 90분 경기를 압축.
- **측정 스크립트**: 각 상태에서 DOM 전수 검사 — ① 뷰포트 밖으로 나간 요소 ② 스크롤/클립으로 숨겨진 비율 ③ 텍스트 대비비(WCAG) ④ **박스 겹침**(면적 20% 초과 교차) ⑤ 터치 타깃 크기 ⑥ line-height < font-size(한글 글리프 잘림).
- **뷰포트**: 3456×2160 / 1920×1080 / 1440×900 / 390×844. OS 테마는 **라이트**(중요 — R1이 라이트에서만 발현).
- **한계 / 확인 필요**: ① 엔딩 화면은 캠페인 8경기 완주가 필요해 코드 리뷰만 했다(시각 확인 필요). ② 대비비 자동 측정은 조상이 전부 투명한 경우 배경을 흰색으로 오판한다 — 아래 목록에는 **스크린샷으로 눈으로 확인한 건만** 실었다. ③ 승부차기·연장 화면 미확인.

### 3-A. 문제 정의

제목은 **"현실에서 축덕인 내가, 이세계에선 국대 감독?"** — 이세계 전생 라노벨 밈이다.
내용물은 **실제 대회 데이터·배치 시뮬 검증·방송 중계 문법**을 갖춘 진지한 시뮬레이션이다.

이 둘을 섞는 방법은 세 가지뿐이고, 앞의 둘은 실패한다.

1. **밈을 시각화한다** — 라노벨 UI(핑크·보라·스킬 카드·상태창·컷인)를 얹는다. → 데이터가 장난처럼 보인다. 시뮬레이션의 신뢰가 무너진다.
2. **밈을 지운다** — 순수 FM 클론. → 제목이 거짓말이 되고, 해커톤 심사에서 "왜 이 제목인가"에 답할 수 없다.
3. **밈은 카피에, 진지함은 그래픽에.** ← **이걸 택한다.**

### 3-B. 확정 톤: "정식 국제 중계 그래픽 + 이세계는 문장 안에서만"

> **화면은 FIFA 월드피드처럼 생겼다. 말은 라노벨처럼 한다.**

이세계 요소를 **레이아웃·색·그래픽에 넣지 않는다.** 오직 아래 세 곳에만 넣는다.

| 자리 | 이세계가 하는 일 | 예 |
|---|---|---|
| **화면 제목·섹션 제목** | 장르 어휘를 쓰되 명사구 그대로 | `전생 첫날` / `이세계 벤치` / `소환된 스쿼드` — ※ 명사형 종결("~임/~됨") 금지 |
| **중계·해설·기자 대사** | 문체로 밈을 실현. 그래픽은 손대지 않음 | *"이 세계의 체코는 지지 않습니다."* |
| **전환 순간의 한 문장 카드** | 킥오프 직전 / 하프타임 진입 / 엔딩. 5초 이하 | 검은 화면에 흰 명조 한 줄 |

**하지 않는 것** — 스킬 카드 UI, 상태창 프레임, HP/MP 바, 컷인 이펙트, 판타지 서체, 보라/핑크 팔레트, 아이콘으로서의 이모지.

**근거 (검증됨)**: 2026 월드컵 브랜드 아이덴티티는 FIFA 역사상 가장 채도가 높지만, **상시 노출되는 스코어버그는 검정 바 + 흰 타입 + teal/gold 슬리버뿐**이다. 리뷰어 표현으로 *"dressed for a board meeting."* 가장 화려한 브랜드도 정보 그래픽에서는 뉴트럴로 후퇴한다.
→ 우리도 같은 규칙을 쓴다. **브랜드(이세계)는 타이틀과 카피에서 크게, 정보 그래픽에서는 침묵한다.**
출처: <https://www.colorwaysports.com/stories/world-cup-2026-scorebug-review>

### 3-C. 조사에서 가져오는 원칙 (전부 검증된 1차 소스)

| 원칙 | 소스 문장 | 우리 적용 |
|---|---|---|

| **킷 컬러 칩** | 2026이 국기·약어와 **별개로** 얇은 킷 색 스트립을 넣은 이유: *"answer the question the viewer hasn't consciously formed yet"* = 필드에서 어느 색을 따라갈 것인가 | 스코어버그에 3px 킷 스트립을 넣고, **피치 위 도트 색과 반드시 일치**시킨다 |
| **상시 버그는 action-safe 코너** | *"If the station uses a permanent digital on-screen graphic, it is placed just near the corner of the action-safe area."* | 스코어버그를 좌상단, 각 변 3~4% 인셋 |

## 4. 기존 토큰 평가 (`src/ui/tokens.css`)

```css
--bc-bg:#0b1220  --bc-panel:#121c30  --bc-panel-2:#1a2742  --bc-line:#2a3a5c
--bc-text:#e8edf6  --bc-text-dim:#8fa0bd  --bc-accent:#c8f542  --bc-danger:#ff5d5d
--bc-pitch:#1e7a3c  --bc-pitch-line:rgba(255,255,255,.55)
--bc-home:#e63946  --bc-away:#4895ef  --bc-font:"Apple SD Gothic Neo",...
```

**살릴 것**
- 배경 3단(`bg` → `panel` → `panel-2`) + `line`의 **구조**는 옳다. UCL이 "야간 경기"를 근거로 다크 네이비를 택한 것과 같은 방향.
- `--bc-text` / `--bc-text-dim` 2단 텍스트 위계도 옳다.
- 값 자체도 대체로 쓸 만하다(`#0b1220`, `#e8edf6`).

**버릴 것 / 고칠 것**

| 문제 | 진단 |
|---|---|
| **토큰이 12개뿐** | 간격·타입·radius·모션·z-index 토큰이 아예 없다. 그래서 42종 hex / 26종 font-size / 15종 radius가 생겼다 |
| **`--bc-accent`가 과부하** | 주석은 "경기 화면 한정"인데 실제로는 CTA·선택·탭·체력바·수비라인·압박존·데모배너·기자회견 버블. 한 토큰이 8가지 뜻을 가지면 위계가 성립하지 않는다 |
| **`--bc-home`이 팀색이자 위험색** | `#e63946` vs `--bc-danger:#ff5d5d`. 육안 구분 불가 |
| **팀색이 하드코딩** | 대한민국이 아닌 팀끼리 붙으면? `--bc-home/away`는 팀 상수가 아니라 **경기별로 주입돼야 할 런타임 값**이다 |
| **`--bc-pitch`는 있는데 실제 피치는 4종** | 3D 잔디 / 라인업 보드 형광초록 / 미니맵 네이비 / 작전판 초크블루. 토큰이 강제력을 못 가짐 |
| **`--bc-font`가 시스템 한글 폰트 단일** | 숫자용 tabular figures가 없다. "Apple SD Gothic Neo"는 macOS 전용이라 Windows/Android에서 폴백이 갈린다 |
| **라이트 테마 방어가 없다** | `index.css`의 라이트 값이 새어 들어와도 막을 장치가 없음 (G-1, G-2) |

**결론: 구조는 유지하고 어휘를 3배로 늘린다. 그리고 `index.css`의 스캐폴드를 제거한다.**

## 5. 디자인 시스템 명세

파랑은 포인트 컬러로 **유지**한다(사용자 지시).
아래 팔레트에서 **파랑이 브랜드 액센트이고, 라임은 라이브 상태 전용으로 강등**된다.

### 5-A. 색 — 역할별

색에 **뜻을 하나씩만** 준다. 이것이 A-1(범례 불가능) 문제의 유일한 해법이다.

#### 표면 (야간 경기장)

| 토큰 | 값 | 용도 |
|---|---|---|
| `--s-0` | `#070C15` | 페이지 배경. 현재 `#0b1220`보다 한 단계 더 내려 패널이 뜨게 함 |
| `--s-1` | `#0E1626` | 기본 패널 |
| `--s-2` | `#16203440` | 패널 위 패널(반투명). 3단 이상 중첩 금지 |
| `--s-line` | `#243350` | 헤어라인 |
| `--s-line-strong` | `#38507C` | 활성 테두리 |
| `--s-scrim` | `rgba(4,8,16,.72)` | 3D 위 텍스트 스크림 |

#### 텍스트

| 토큰 | 값 | 대비(on `--s-1`) |
|---|---|---|
| `--t-hi` | `#F2F6FF` | 16.9:1 |
| `--t-mid` | `#AEBED8` | 8.4:1 |
| `--t-low` | `#7387A8` | 4.6:1 — **캡션 최소선. 이보다 흐린 텍스트 금지** |

#### 브랜드 / 상태 — **각 색은 뜻이 하나다**

| 토큰 | 값 | 유일한 뜻 | 금지 |
|---|---|---|---|
| `--brand` | `#3B82F6` | **감독의 행동** — 주 CTA, 선택된 옵션, 포커스 링 | 데이터 시각화에 사용 금지 |
| `--brand-ink` | `#0A1220` | `--brand` 위 텍스트 | |
| `--live` | `#C8F542` | **"지금 진행 중"** — LIVE 도트, 경과 시계, 재생 중 표시 | **CTA·선택 상태·데이터 색으로 사용 금지** |
| `--warn` | `#F5B830` | 경고, 옐로카드, 체력 저하 | |
| `--danger` | `#FF4D4D` | **레드카드·실점·부상만.** 방송 관례대로 "경기 중 가장 큰 소리" | 팀 색·일반 오류 금지 |
| `--good` | `#2ED573` | 득점, 개선, 성공 | |
| `--gold` | `#E6B450` | **대회/중대 상태** — 승리, 진출 확정, 트로피 |

**근거**: 2026 월드컵 스코어버그는 빨강을 추가시간 칩과 레드카드에만, 골드를 트로피와 "DOWN TO 10 PLAYERS" 배너에만 쓴다. 색의 희소성이 곧 의미다.

#### 팀 색 — **토큰이 아니라 런타임 변수**

```css
/* 경기 시작 시 팀 데이터에서 주입. 상수로 박지 않는다. */
--team-us:   #E03131;  /* 예: 대한민국 */
--team-them: #2B6CB0;  /* 예: 체코 */
--team-us-ink / --team-them-ink  /* 각 색 위 텍스트 */
```

규칙:
1. 팀 색은 **선수 도트, 스코어버그 킷 스트립(3px), 점유율 바** 세 곳에만 쓴다.
2. 두 팀 색의 **ΔE < 25면 원정팀에 대체 색을 자동 배정**한다(한국 빨강 vs 스페인 빨강 대비).
3. 흰색 킷은 반드시 **1px 다크 아웃라인**을 넣는다. *(2026 월드컵에서 흰 킷 스트립이 흰 시계 pill과 붙어 구분 안 되는 사고가 실제로 발생했다.)*
4. **팀 색을 텍스트 색으로 쓰지 않는다** (F-2 해결). 스탯 표의 숫자는 `--t-hi`, 소속은 좌우 위치와 상단 킷 칩으로 표현한다.

#### 전술 분석 레이어 — **재배정 (A-1 해결)**

빨강·라임을 회수하고, 분석 그래픽에는 **팀 색에서 파생한 색과 형태**를 쓴다.

| 그래픽 | 새 표현 | 왜 |
|---|---|---|
| 우리 수비 라인 | `--team-us` **실선** + 라인 위 라벨 플레이트 | 팀 색이면 "누구 라인인지"를 색이 직접 말한다 |
| 상대 수비 라인 | `--team-them` **실선** | 대칭 |
| 압박 존 | 해당 팀 색 **8% 채움 + 12% 스트로크** | 라인과 같은 색군 = "같은 팀 이야기" |
| 패스 레인 화살표 | **`--t-hi` 흰색 실선/파선** (채움 아님) | 경로는 팀 소속이 아니라 **계획**이다. 흰색은 방송 텔레스트레이션 관례 |
| 공격 집중 밴드 | `--t-hi` **4% 채움** | 위와 같은 이유 |
| 침투(dashed) vs 전개(solid) | **선 스타일로 구분**, 색은 동일 | 색은 소속, 형태는 종류 |

→ **색 = 누구(팀), 형태 = 무엇(라인/존/경로).** 이제 범례가 3줄로 끝난다.

#### 범례 컴포넌트 (신규, A-1)

작전판·2D 화면 **우하단 고정**, 접을 수 있고 기본 펼침. 40×12px 샘플 + 한글 라벨.

```
┌───────────────────────────────┐
│  ▬▬▬  대한민국 수비 라인  50   │
│  ▬▬▬  체코 수비 라인      62   │
│  ▒▒▒  압박 범위                │
│  ⟶    계획한 전개 경로         │
│  ⇢     침투(뒷공간)            │
└───────────────────────────────┘
```

### 5-B. 타이포그래피

**서체 2종 체계** (근거: PL은 본문/숫자 지오메트릭 + 긴 이름용 Condensed를 **같은 패밀리 안에서 분리**했고, UCL은 디스플레이/정보/감성 3축으로 분리했다.)

```css
--f-ui:  "Pretendard Variable", Pretendard, "Apple SD Gothic Neo",
         "Noto Sans KR", system-ui, sans-serif;   /* 모든 UI 텍스트 */
--f-num: "Roboto Mono", "SF Mono", ui-monospace, monospace; /* 숫자 전용 */
--f-display: "Pretendard Variable";  /* 타이틀 — 굵기와 자간으로 구분 */
```

- **Pretendard를 자산으로 번들**한다. 현재 `Apple SD Gothic Neo`는 macOS 전용이라 Windows에서 맑은 고딕으로 떨어져 자간·굵기가 전부 달라진다.
- **숫자는 전부 tabular**:
  ```css
  .num { font-variant-numeric: tabular-nums lining-nums; font-feature-settings: "tnum" 1, "lnum" 1; }
  ```
  적용 대상: 스코어, 시계, 분(minute) 배지, 스탯 표, 순위, 등번호.
  *근거: Toshi Omagari(Premier Sans) — "We knew that it would be used a lot on TV and mobile, so it was essential that **numbers be different and distinct**." 시계에서 프로포셔널 숫자를 쓰면 1이 나올 때마다 컨테이너 폭이 흔들린다.*
- **condensed 금지, weight 800 이상 금지** — 작은 크기의 숫자에 한해. *근거: FIFA 2026이 Ultra Condensed Black을 스코어에 썼다가 0↔8 오독으로 숫자만 Noto Sans로 교체.*

**스케일** — 26종을 **9종**으로 줄인다. 전부 px(rem 금지 — G-6 재발 방지).

| 토큰 | px | line-height | 용도 |
|---|---|---|---|
| `--fs-display` | `clamp(32px, 4vw, 56px)` | 1.12 | 랜딩 타이틀, 엔딩 헤드라인 |
| `--fs-score` | `clamp(28px, 2.6vw, 44px)` | 1.0 | 스코어. tabular |
| `--fs-h1` | 24 | 1.3 | 화면 제목 |
| `--fs-h2` | 18 | 1.4 | 섹션 제목 |
| `--fs-lg` | 16 | 1.6 | 강조 본문, 중계 티커 |
| `--fs-md` | 14 | 1.6 | **기본 본문** (현재 12~13px에서 상향) |
| `--fs-sm` | 13 | 1.5 | 보조 |
| `--fs-xs` | 12 | 1.4 | 라벨, 배지. **최소값 — 이하 금지** |
| `--fs-eyebrow` | 12 | 1.4 | 대문자/자간 0.08em 키커 |

- **한글 line-height 최소 1.4** (G/E-6 해결: 현재 24px 글자에 26.1px 행간이 잘림을 만든다).
- 자간: 본문 0, 대문자/약어 `+0.04em`, 디스플레이 `-0.02em`.
  *근거: FIFA 2026의 tricode 판독 실패 원인이 자간 부족이었다.*

### 5-C. 간격 · 그리드 · radius · 모션

**간격 — 4px 베이스 8단**
```
--sp-1:4  --sp-2:8  --sp-3:12  --sp-4:16  --sp-5:24  --sp-6:32  --sp-7:48  --sp-8:64
```
16종 gap → 이 8개만. 컴포넌트 내부 `--sp-2`/`--sp-3`, 컴포넌트 간 `--sp-4`/`--sp-5`, 섹션 간 `--sp-6`+.

**radius — 4단**
```
--r-sm:6   칩·배지·인풋
--r-md:10  카드·버튼
--r-lg:16  패널·모달
--r-pill:999px
```
15종 → 4종. `50%`는 원형 도트만. `14px 14px 4px 14px` 같은 비대칭은 **금지**.

**모션**
```
--dur-1:120ms  마이크로(호버·포커스)
--dur-2:220ms  컴포넌트 진입/퇴장
--dur-3:400ms  화면 전환
--dur-4:800ms  연출(입장·득점)
--ease-out:  cubic-bezier(.16,1,.3,1)   진입
--ease-in:   cubic-bezier(.7,0,.84,0)   퇴장
--ease-io:   cubic-bezier(.65,0,.35,1)  이동
```
원칙:
1. **스코어 숫자는 애니메이션하지 않는다.** 1순위 정보는 언제나 즉시 읽혀야 한다.
2. 득점·카드 시 **새 그래픽을 추가하지 말고 스코어버그를 변형**시켰다 6~10초 후 base state로 복귀시킨다. *(LaPlante의 "일시적 위계" 원리, TNT NBA 방식)*
3. `prefers-reduced-motion: reduce`에서 `--dur-*`을 전부 `1ms`로 덮고 `transition/animation`이 아닌 상태 전환만 남긴다. **현재는 파일마다 개별 대응이라 누락이 생긴다 — 토큰 레벨에서 한 번에 끈다.**

**레이아웃 그리드 — R2/R5의 구조적 해법**

> 진단: 겹침과 잘림은 **"높이를 예산으로 배분"** 하는 설계에서 나온다.
> `.ms-root{height:100vh}` → `.ms-stage{overflow:hidden}` → `.ms-precenter{overflow-y:auto}` → `.tc-war{max-height:38vh; overflow:hidden}` → `.tc-war__body{overflow-y:auto}` → `.lu-bench{overflow:auto}`.
> **중첩 스크롤 컨테이너가 5단**이다. 각 단계에서 남는 높이를 나눠 가지므로, 뷰포트가 1px 줄면 가장 안쪽이 먼저 죽는다.

**규칙 1 — 스크롤은 문서가 한다.**
`height:100vh`를 전부 `min-height:100dvh`로 바꾼다. 페이지는 세로로 자란다. 내부 스크롤 컨테이너는 **화면당 최대 1개**만 허용하고, 그 하나에는 반드시 아래를 붙인다:
- 가시 스크롤바(`scrollbar-color`) 또는 상하 페이드 마스크
- 스크롤 가능함을 알리는 상단/하단 그림자
- 헤더에 `N / 전체` 카운트

**규칙 2 — 3층 셸.**
```
┌──────────────────────────────────────────┐
│ [고정] 상단 방송 furniture (56px)         │  스코어버그·시계·속도·오디오
├──────────────────────────────────────────┤
│                                          │
│ [흐름] 콘텐츠 — 문서 스크롤              │
│                                          │
├──────────────────────────────────────────┤
│ [고정] 하단 액션 바 (64px)                │  주 CTA 1개 + 상태 1줄
└──────────────────────────────────────────┘
```
상·하단만 `position: sticky`. 중간은 자유롭게 자란다. 티커는 하단 바 **안**으로 들어간다(현재는 별도 레이어라 T-2 겹침을 만든다).

**규칙 3 — 콘텐츠 폭 상한과 열 시스템.**
```css
--w-content: 1440px;   /* 텍스트 위주 화면 */
--w-wide:    1760px;   /* 워룸·경기 등 밀도 높은 화면 */
```
`#root{max-width:1920px}` 대신 화면별 상한을 쓴다. 3456px에서 좌우 검정 여백 대신 **패널이 자란다**.

12열 그리드, gutter `--sp-4`. 브레이크포인트 4개:

| 이름 | 범위 | 워룸 레이아웃 |
|---|---|---|
| `sm` | < 720 | **1열 세로 스택** + 하단 탭바로 섹션 전환 |
| `md` | 720–1199 | 2열 (설계 8 / 상대 4), 벤치는 접이식 |
| `lg` | 1200–1679 | 3열 (상대 3 / 보드 6 / 벤치 3) |
| `xl` | ≥ 1680 | 3열, 보드가 커지고 벤치 2열 카드 |

**규칙 4 — 겹침 금지 규약.**
- 절대배치(`position:absolute`)는 **3D/2D 캔버스 위 오버레이에만** 허용한다. 그 외 UI는 전부 flow/grid.
- 오버레이가 뜨면 그 아래 furniture는 **숨기거나 `pointer-events:none`으로 죽이지 말고 실제로 언마운트**한다 (T-2).
- z-index를 토큰화: `--z-base:0 --z-furniture:10 --z-overlay:40 --z-modal:60 --z-toast:80`.

**규칙 5 — SVG 위 텍스트는 항상 플레이트나 후광을 갖는다.**
```css
.on-pitch-label {
  paint-order: stroke fill;
  stroke: rgba(4,8,16,.85); stroke-width: 0.6; stroke-linejoin: round;
}
```
그리고 **충돌 회피**: 라인 태그와 선수 이름이 같은 밴드에 오면 라인 태그를 반대편 터치라인으로 이동시킨다 (A-2/A-3 해결).

### 5-D. 컴포넌트 패턴

#### 카드 — **좌측 컬러 띠 금지**
사용자가 금지한 "컬러 좌측 띠 + 회색 카드"를 대체하는 4가지:

| 대신 쓸 것 | 설명 |
|---|---|
| **아이보로우(eyebrow) 라벨** | 카드 상단에 12px/자간 .08em 대문자 라벨 + 색은 텍스트에만. 띠 없음 |
| **테두리 전체 색조** | 카드 `border-color`를 상태색 24%로. 좌측만이 아니라 4변 전부 |
| **배경 틴트** | 상태색 `6%` 채움 + 상태색 `20%` 헤어라인. 회색 카드가 아니라 색조 카드 |
| **헤어라인 구획** | 카드를 없애고 상단 1px 라인 + 제목 타이포 위계만으로 구획 (허브 여정 사다리가 이미 이 방식이고, 옳다) |

기본 카드:
```css
.card { background: var(--s-1); border: 1px solid var(--s-line);
        border-radius: var(--r-md); padding: var(--sp-4); }
.card--warn { border-color: color-mix(in srgb, var(--warn) 34%, transparent);
              background: color-mix(in srgb, var(--warn) 6%, var(--s-1)); }
```

#### 버튼 — 4종만

| 종류 | 스타일 | 화면당 개수 |
|---|---|---|
| `primary` | `--brand` 채움 / `--brand-ink` 텍스트 | **최대 1개** |
| `secondary` | 투명 / `--s-line-strong` 테두리 / `--t-hi` | 제한 없음 |
| `ghost` | 투명 / 테두리 없음 / `--t-mid` | 제한 없음 |
| `danger` | `--danger` 테두리 + 텍스트 | 파괴적 동작만 |

- 높이 3단: `sm 32 / md 40 / lg 48`. 터치 타깃은 **최소 44×44**를 `::before` 확장으로 보장(G-9).
- 점선 테두리 버튼 **폐지**(T-6). 라임 채움 버튼 **폐지**(라임은 `--live` 전용).
- **화면당 primary는 하나.** T-6의 4중 커밋 문제는 이 규칙 하나로 사라진다.

#### 탭 / 세그먼트
- 탭(비파괴 뷰 전환): 하단 2px 인디케이터 `--brand`, 라벨 `--t-hi`. **번호 접두(①②) 폐지** — 순서를 강제하려면 스텝퍼를 써라.
- 세그먼트(배타 선택, 예 속도 1x/1.5x/2x): pill 컨테이너 + 활성 알약이 이동. 높이 36, 각 셀 최소 44 터치.

#### 배지 / 칩
| 유형 | 규격 |
|---|---|
| 상태 배지 (LIVE, HT, FT) | 높이 22, `--r-sm`, 12px/700, 자간 .06em, 대문자 |
| 포지션 칩 (GK/CB/AM) | 높이 18, 폭 고정 30, tabular, `--s-2` 배경 |
| 포메이션 칩 (4-2-3-1) | 높이 32, tabular, 선택 시 `--brand` |
| 팀 칩 (KOR) | 3px 킷 스트립 + tricode. **국기 이모지 금지 → SVG 스프라이트** |

#### 표
- 헤더 12px `--t-low` 대문자, 본문 14px `--t-hi`, 숫자 tabular **우측 정렬**, 행 구분은 1px `--s-line`(줄무늬 배경 금지).
- **비교 표(팀 A vs 팀 B)는 값을 색칠하지 말고 바로 표현**한다(§5-D 스탯 바 참조).

#### 스탯 바 (F-1 해결, 신규)
```
점유율
KOR ▬▬▬▬▬▬▬▬▬▬▬▬▬░░░░░░░░░  CZE
58%                      42%
```
- 단일 트랙, 좌 `--team-us` / 우 `--team-them`, 높이 8, `--r-pill`.
- 숫자는 **바 양 끝 바깥**에 tabular로. 색칠하지 않는다.
- 근거: 점유율은 합이 100인 **단일 자유도**다. 숫자 두 개는 잉여이고, 바는 "어느 쪽이 얼마나"를 즉시 준다. *(이 특정 논거는 1차 소스 확인 실패 — 논리적 추론임을 밝힌다. 다만 바 사용 자체는 모든 주요 중계 패키지에서 관찰되는 관례다.)*

#### 초기 표본 억제 (사용자 지적 "2분에 점유율 100%")
`< 10분` 또는 `총 패스 < 20`이면:
- 바를 그리되 **50:50 위치에서 실제값으로 서서히 수렴**(damped) 시키고,
- 숫자 대신 **"표본 부족 — 10분부터 집계"** 를 캡션으로 띄운다.
- 또는 **누적 대신 최근 10분 롤링**으로 바꾸고 라벨을 "최근 10분 점유율"로 명시한다.

어느 쪽이든 **UI가 숫자의 신뢰구간을 말해야 한다.** 100%를 그대로 보여주면 시뮬레이션 전체의 신뢰가 깨진다.

#### 스코어버그 — 3단 데크 (2026 월드피드 구조 채택)
```
┌─────────────────────────────────────────┐
│ FIFA WORLD CUP 2026 · 조별 1차전          │ ← 컨텍스트 스트립 12px --t-low
├──────────────┬──────────┬───────────────┤
│ ▌KOR         │   3 : 2  │        CZE ▐  │ ← 본체. ▌= 3px 킷 스트립
├──────────────┴──────────┴───────────────┤
│                              ● LIVE 67' │ ← 시계 pill. 다른 배경색
└─────────────────────────────────────────┘
```
- **시계를 본체와 다른 배경(흰 pill 또는 `--s-0` + `--live` 도트)으로 물리적으로 분리한다.**
  *근거: 시계는 초 단위, 스코어는 이벤트 단위로 갱신 주기가 다르다. 같은 컨테이너에 두면 눈이 매초 스코어 영역을 재스캔한다. 2026 월드피드가 실제로 시계를 흰색 pill에 격리하고 골드 리본으로만 연결한다.*
- 좌상단, 각 변 3~4% 인셋(action-safe 관례).
- 2차 정보(플랜 배지·팀 이해도)는 본체에 얹지 말고 **별도 "game assist" 슬롯**에 둔다. *(NBC Sports가 시스템에 정식으로 정의한 개념)*

## 6. 게임 UI 선례에서 가져올 것 (검증된 조사)

§5의 컴포넌트 명세를 뒷받침하는 사례. **가장 중요한 사실부터**:

### 6-0. FM25는 "UI 논란"이 아니라 **UI 때문에 게임이 통째로 취소됐다**

FM25는 2024년 두 번 연기 후 2025년 2월 **완전 취소**. 30년 연속 출시가 끊겼다.
Miles Jacobson(SI 스튜디오 디렉터)의 사후 인터뷰:

> "The problem was mostly about **user experience (UX) and user interface (UI)**. Even though the back-end simulation worked, the new front-end was 'clunky,' and 'just wasn't fun'. Key information, previously available at a glance, was now hidden behind **'multiple clicks'** … Miles recalled realizing 'within an hour' … he 'literally sat there and just **couldn't find things in my own game**.'"
> — <https://www.fmscout.com/a-miles-jacobson-explains-fm25-cancellation-and-fm26-plans.html>

> "If we had released FM25 in the state that it was in … it would have damaged us forever." / "It's the most expensive decision we've ever made."
> — <https://www.bbc.com/news/articles/c70xd5wl00zo>

FM25가 삭제했다가 FM26에서 **되돌린 것**: 검색 바, 뒤로/앞으로 버튼, 2차 내비게이션, 북마크.
FM26조차 다시 욕을 먹었다 — *"death by dropdown"*, *"a maze of screens"*, *"designed like a cheap mobile game"*, 리그 테이블 확인이 1클릭 → 5클릭.

**우리에게 주는 규칙 4개**
1. **"한 눈에 보이던 정보를 클릭 뒤로 숨기는 리디자인"이 이 장르의 사망 원인이다.** 우리 재설계에서 정보를 접거나 탭 뒤로 보낼 때마다 이 문장을 떠올려라.
2. **핵심 화면 도달 클릭 수를 수치 지표로 잡아라.** (예: 랜딩→킥오프 ≤ 3클릭, 경기 중→교체 실행 ≤ 2클릭)
3. Jacobson이 복구된 내비를 *"feels like a warm hug"*라 표현한 것 — 목표는 참신함이 아니라 **익숙함**이다.
4. 데스크톱과 모바일에 같은 레이아웃을 강요하지 마라 (eFootball이 같은 병으로 성토당했다).

### 6-1. ★ 피치 위 이름 충돌 — FM/EA의 실제 해법 (A-2·T-7·W-8 처방의 근거)

**FM은 이름을 라인 "옆에 피해서" 놓지 않는다. 이름을 담은 불투명 카드로 라인을 가려버린다.**

```
        ┌──[셔츠 아이콘 + 등번호]──┐   ← 카드 상단에 반쯤 걸침
   ┌────┴───────────────────────┴────┐
   │ ♥   DLF - At              ★2.5  │  ← 역할약어 - 듀티(듀티만 색상)
   │     Ferguson                    │  ← 성(姓)
   └─────────────────────────────────┘  ← 라인별 색으로 채운 불투명 카드
```
- 카드 배경색 = **포지션 라인 인코딩**(공격 보라 / 중원 진회색 / 수비 파랑 / GK 올리브).
- 색은 **듀티에만** 적용, 역할 약어는 흰색 → 색 채널 2개 유지.
- **FM26은 포메이션 카드의 피치를 초록이 아니라 다크 네이비 + 얇은 흰 선으로 그린다** — 라인 대비 자체를 낮춰 텍스트 가독성을 확보.
- 그리고 결정적으로: **FM은 라이브 2D/3D 피치에 이름을 아예 안 쓴다.** FM26 경기 중 3D HUD는 `Leave Match` + 스코어 bug + 설정 + 하단 커멘터리 알약, 그게 전부. 2D 오버뷰의 토큰은 **등번호만**이고 이름은 옆 Formation 카드에 있다. FM24 3D는 볼 근처 몇 명만 반투명 알약 라벨을 띄우고, 전원 표시는 옵트인이다.
- **세트피스 화면의 "코드 토큰" 기법**: 좌측 지시 리스트의 각 행 앞에 `B0 B1 C0 D1` 색상 코드 칩을 붙이고, 우측 확대 피치의 마커에는 **같은 코드만** 찍는다. **이름을 피치에서 완전히 추방하고 좌측 리스트가 곧 범례가 된다.**
- **EA FC의 기하학적 트릭**: 피치를 탑다운이 아니라 **사다리꼴 원근**으로 그려 앞(수비)을 넓히고 뒤(공격)를 좁힌다 → 11개 카드가 자연스럽게 세로로 벌어진다. 단 EA도 **고정폭 카드 + 긴 역할명에서 단어 중간 잘림**("ide Midfielder", "ying Playmaker")을 당했다 — 약어 사전이 필수.

### 6-3. "보는 모드"와 "읽는 모드"의 시간축 분리 (M-1·M-2 처방의 근거)

- **하이라이트 사이(읽는 모드)**: `Match Overview` 대시보드 — 양 팀 Formation 카드 · Match Stats(대칭 발산 바) · Match Events · 2D 피치(등번호 토큰) · Dugout 제안 카드 · 온피치 칩 스트립.

**한 화면에 둘 다 넣지 않는다.** 지금 우리 경기 화면은 둘을 동시에 하려다 둘 다 실패하고 있다.

**Dugout 카드**가 특히 좋다 — 어시스턴트 조언을 텍스트로 흘리지 않고 `제목 / 본문 1줄 / [✓ Do it] [✕] [▼]`로 **원클릭 실행 가능한 카드**로 만든다. 우리 `코치 회의`(T-10)를 이 형태로 바꾸면 금지된 좌측 띠 카드도 같이 사라진다.

### 6-4. 터치라인 외침 (M-6 처방의 근거)

### 6-5. 전술 입력 (W-13·W-14 처방의 근거)

- **OSM**: 슬라이더 대신 **라인별 3택 세그먼트** — 공격진 `Attack Only / Support Midfield / Drop Deep`, 중원 `Push Forward / Stay in Position / Protect Defense`, 수비 `Attacking Full Backs / Support Midfield / Defend Deep`. 이산 값이라 터치 타깃이 크고, **직렬화와 AI 브리핑에도 유리**하다.
- **EA FC**: 이산 프리셋 4개 + 연속 슬라이더 1~100을 **한 컨트롤에** — Deep(1–30) / Balanced(31–60) / High(61–90) / Aggressive(91–100). **초보는 버튼, 고수는 슬라이더.** 우리 라인/압박/템포 슬라이더에 그대로 적용 가능.
- **EA FC `Reset Tactic`** = 화면 진입 시점 스냅샷으로 롤백. 저비용/고효용.
- **EA FC Tactics Code** — 전술 전체를 11자리 코드로 직렬화, 공유. 브라우저면 URL 쿼리스트링으로 거의 공짜다. **해커톤 시연·심사에서 값이 크다.**
- **EA FC 피치 아래 "강점 3 / 약점 3" 자동 문장** (초록 ✓ / 노랑 !) — 우리 하단 검토 요약(W-11)을 이 형태로 바꾸면 4열 불균형이 해소된다.
- **eFootball의 교훈(반면교사)**: 선수를 자유 배치할 수 있지만 엔진은 여전히 베이스 포메이션으로 판정하고 **UI가 그 불일치를 알려주지 않는다.** → 자유 드래그를 허용한다면 "현재 배치가 어떤 포메이션으로 판정되는지"를 라이브로 표시해야 한다.

### 6-6. 하프/풀타임 리포트 (F-1·F-5 처방의 근거)

FM26 26.1.1이 리포트 화면을 재작업하며 확정한 블록 순서:
**스코어+득점자 → 선수 평점(양 팀) → 통계 → 리그 컨텍스트.**
그리고 방송 표준 통계 순서(Broadage 방송사 납품 위젯 규격):
**점유율 → 슛(온/오프) → 파울 → 코너 → 오프사이드 → 선방 → 카드.**
표현 규칙 원문: *"data appears both with **numbers and bars**"*, *"maximum length for bars are **relative for both team**"* — 즉 **항목마다 두 팀 합을 100%로 정규화한 대칭 발산 바**.

FM26 `Match Momentum`: 중앙선 기준 상/하 발산 막대 + `1st Half`/`2nd Half` 축 + 팀 색 도트 범례 + **`👍 Better` 한 단어 판정 칩**.

⚠️ FM 고질 불만: **팀토크 후 하프타임 통계로 돌아갈 수 없다** → 결정(팀토크·전술)과 정보(리포트)를 분리하되 **왕복 가능**해야 한다.

### 6-7. 전술보드 선/화살표 — "표준"은 없다, 그래서 범례가 필수다

정반대 두 진영이 실존한다:
- **진영 A**(드릴 출판): 실선 = 선수 런, 파선 = 패스 — <https://elitechampionscoaching.com/coaching-tools/soccer-set-piece-diagrams/>
- **진영 B**(US Soccer 체계, Opta/StatsBomb 패스맵): 실선 = 볼 궤적, 파선 = 오프더볼 이동 — <https://coachingamericansoccer.com/tactics-and-teamwork/soccer-diagramming/>
- **양 진영이 합의하는 유일한 항목: 물결선 = 드리블.**

작도 원칙(검증됨) — <https://hobbit.football/tools/soccer-drill-diagram-symbols-explained>
> "Keep ball arrows visually distinct from player arrows (**different line style, often different colour**)" / 순서 있는 움직임은 화살표에 번호(1,2,3) / 복잡하면 phase별로 쪼갠다 / **"Add a legend or caption at the bottom… Without this, the drawing is just shapes."**

우리는 **진영 B**를 택한다(데이터 시각화 관례이고 Opta/StatsBomb과 일치).

| 선 스타일 | 의미 |
|---|---|
| 실선 + 화살촉 | **볼 이동(패스)** |
| 물결선 + 화살촉 | **드리블** |
| 파선 + 화살촉 | **오프더볼 런** |
| 굵은 앰버 실선 | **슛** |
| 점선(화살촉 없음) | 패싱 레인 / 커버 섀도 |

색맹 안전 팔레트(mplsoccer 사실상 표준, 검증됨): 성공 딥틸 `#0a5a3f` / 실패 클레이 `#B4553C` / GK 노랑 `#F2C230` / 다크 피치 `#22312b` + 라인 `#efefef`.
**적록 대비를 쓰지 않는다.**

⚠️ FM 자신의 오버레이는 범례를 거의 안 띄우고 **그게 실제 불만이다** — SI 버그트래커 FM26: *"there are a fair number of stats only shown as relative stats. Those values are meaningless if we have no idea what their **sample size** is."* → 우리는 범례를 기본 노출하고 분모를 병기한다.

### 6-8. 초반 점유율 (사용자 지적 "2분에 100%") — 검증된 처방

**중요: 방송도 게임도 억제하지 않는다.** Opta/Stats Perform 공개 문서와 방송 위젯 규격 어디에도 "N분 전까지 미표시" 규칙이 없다. 실시간 피드를 그대로 흘린다.
→ **즉 이건 우리가 방송보다 잘할 수 있는 지점이고, 해커톤에서 차별점이 된다.**

배경 사실(검증됨):
- 점유율 정의가 3종 공존(passing time / ball-touch time + 0.3~0.5초 버퍼 / event-count ratio)이고 **같은 경기에서 제공사 간 4~6%p 차이**가 난다 → **소수점 금지, 5%p 눈금 권장.**
- Opta 정의: *Sequence* = 한 팀에 속한 연속 플레이, 수비 액션·정지·슛으로 종료. *Possession* = 같은 팀의 연속 sequence 묶음. → **possession 개수가 자연스러운 표본 카운터.**
- **Opta Match Momentum이 모범 답안**: 분당 possession value를 클리핑 후 차분하고, *"only the most recent three to four minutes have significant impact"*, 목적은 *"to avoid large fluctuations in momentum between each minute"*.
- mplsoccer 규범: *"Sparse bins should show no arrow rather than a misleading direction from few passes"* / *"Zero-event selections should be marked unavailable or empty"* / **"label the denominator"**.
- **xG는 억제 불필요** — 0에서 시작해 슛마다 계단으로 오르는 누적량이라 1분부터 정직하다.

**구현 규칙**
```
게이트 A (하드 억제)   t < 5분 AND 총 possession < 20
   → 값 "—", 바는 50:50 회색 고정, 캡션 "집계 중"

게이트 B (수축)        5 ≤ t < 15분
   p_shown = (t_home + k·0.5·T) / (t_home + t_away + k·T),  k = 0.5
   → 3분 시점 100:0 원본이 약 67:33으로 수축, 15분엔 원본에 ~90% 수렴
   불확실 밴드 폭 = 1.96·sqrt(p(1-p)/n_poss)
   (n=10 → ±30%p, n=40 → ±15%p, n=100 → ±10%p)

게이트 C               t ≥ 15분 → 원본값, 정수 반올림, 밴드 제거

보조: 최근 5분 롤링 점유율 / 모멘텀 막대(1분부터 정직) / 누적 xG 계단선
      이벤트 0건이면 빈 상태(0을 색칠 금지) / 모든 % 옆에 분모 병기 "62% (24/39)"
```
**한 줄 원칙: 누적량(xG·슛·패스 수)은 1분부터 정직하다. 억제·수축 대상은 비율(%)과 방향 평균뿐이다.**

### 7-3. 전술 센터 / 워룸 — **가장 많은 시간을 쓸 화면**

**현재 문제**: 900px 안에 ①3D 스타디움 띠 ②상대 리포트 ③탭 ④포메이션 보드 ⑤벤치 ⑥검토 요약 ⑦티커를 전부 넣으려다 5단 중첩 스크롤이 생겼다.

**핵심 결정 3개**

1. **3D 스타디움 띠를 삭제한다.** 킥오프 전 화면의 주인공은 설계이고, 190px짜리 극단 레터박스 3D는 정보가 0인데 높이 예산의 21%를 먹는다. 방송 정체성은 **상단 바의 스코어버그(pre 상태)와 하단 티커**가 이미 담당한다. 필요하면 상단 바 배경에 **정지 스타디움 스틸 이미지 + 40% 다크 오버레이**로 대체(높이 56px).
2. **문서 스크롤로 전환한다.** 세로로 길어져도 된다. 내부 스크롤은 벤치 하나만 허용.
3. **탭 2개(`선발`/`팀 전술`)를 없애고 한 페이지 세로 흐름으로 편다.** FM25의 사망 원인이 "클릭 뒤로 숨기기"였다. `선발 → 팀 전술 → 검토`는 순차 작업이지 배타 뷰가 아니다.

| 5-4 | 390px 전 화면 실측 재검증 |
| 5-5 | **선택**: 전술 short code 직렬화(URL 공유) — 시연 가치 |

### 회귀 방지 (권장)

1. **CSS 린트 규칙**: 하드코딩 hex 금지, `var(--*)`만 허용. font-size는 `--fs-*`만.
2. **레이아웃 스모크 테스트**: 이 감사에 쓴 Playwright 측정 스크립트를 CI에 넣어 4개 뷰포트 × 주요 상태에서 **겹침 0건 / 은닉 0건 / 대비 4.5:1 이상**을 검증. 스크립트는 `docs/audit/`에 있다.
3. **클릭 수 예산**: 랜딩→킥오프 ≤ 3, 경기 중→교체 실행 ≤ 2. FM25의 사망 원인이 이 지표였다.

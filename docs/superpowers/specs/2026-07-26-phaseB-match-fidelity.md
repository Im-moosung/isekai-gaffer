## Phase B의 재정의

원래 Phase B는 "방송 품질"이었다 — UEFA 규격 카메라, 잔디 스트라이프, 리플레이 링버퍼, 샷 디렉터. 전부 `docs/audit/3d-render-research.md`에 리서치가 끝나 있다.

**그러나 그 전제가 틀렸다.** 카메라·잔디는 "밑에서 도는 움직임은 이미 경기를 반영한다"를 가정하는데, 실제로는 아니다. 사용자 지적:

> "공이 자기 혼자 돌아다니고 중계 메시지에 골키퍼가 막았다 이런데, 실제로는 그거랑 전혀 상관없이 플레이가 되고 있고"

**카메라를 아무리 잘 잡아도 공이 8자를 그리고 있으면 소용없다.** Phase B를 "경기 화면이 경기와 일치하게 만들기"로 재정의한다.

## 진단 — 소스로 확인한 사실

### D1. 이벤트 없는 분에는 공이 리사주 곡선을 그린다

`src/ui/pitch/three/movement.ts:226` `idleBall()`:
```js
const phase = (minute + t) * 0.9 + unit(`ball:${seed}`) * TAU
x = clamp(drift + Math.cos(phase) * 14, …)
z = clamp(Math.sin(phase * 0.8) * 12, …)
```
축구가 아니라 장식용 진동이다. `drift`만 모멘텀을 반영한다.

발생 빈도: 경기당 슛 약 24개(양팀), 파울 약 22개, 코너 약 9개. 분이 겹치는 것을 감안해도 **90분 중 대략 50~60분은 이벤트가 없다.** `fastForward`(`MatchScreen.tsx:361`)가 이벤트 없는 분을 빠르게 넘기지만, 1x에서 90분을 3~5분에 소화하므로 여전히 상당한 화면 시간이 리사주에 쓰인다.

### D2. 선택자가 셋이고 서로 다른 이벤트를 고를 수 있다

| 계층 | 무엇을 고르나 | 위치 |
|---|---|---|
| 티커 | 그 분의 **모든** 이벤트 | `MatchScreen.tsx` `minuteEvents` |
| TTS | 대표 **1개** | `ctts.pickSpokenEvent(eventsAtMinute)` |
| 안무 | `EVENT_DWELL_MS` 최댓값 **1개** | `MatchScreen.tsx:225-238` `highlight` |

한 분에 `shot` + `save` + `corner`가 함께 나면 음성은 "골키퍼가 막았습니다"인데 화면은 코너 안무를 돌 수 있다. 사용자가 본 증상이 이것이다.

### D3. 안무가 있는 이벤트 타입이 5종뿐이다

`src/ui/pitch/choreography.ts:71` `switch`: `goal` / `miss` / `save` / `corner` / `foul`·`yellow`·`red`.
`shot` · `chance` · `sub` · `kickoff` · `halftime` · `fulltime`은 안무가 없다.

### D4. 두뇌와 표현이 서로 다른 보폭 모델을 쓴다

- `movement.ts:554` — 거리 기반으로 `actionT` 누적: `actionT = (prev + speed*dt / STRIDE) % 1`, `STRIDE = 2.2` (상수)
- `player3d.ts` `case 'run'` — **이 `actionT`를 읽지 않고** 자체 `phase`를 `advancePhase()`로 적분. 보폭 모델도 다르다: `strideLength(speed) = 1.1 + 0.28*speed` (속도 6에서 2.78 m)

**run의 `actionT`는 현재 죽은 값이다.** 발 미끄러짐의 뿌리이며, D1과 같은 종류의 결함이다 — 두뇌가 계산한 것을 표현이 무시한다.

## 리깅 에셋 — 도입 보류 (조사 완료 2026-07-26)

**결론: 도입하지 않는다.** 근거 둘.

**1. 라이선스.** Mixamo는 Adobe 일반 약관 §3.6(2025-10-03 발효)에서 `non-sublicensable`·`non-transferable`이며 *"under no circumstances can you distribute the Content Files on a stand-alone basis, outside of the End Use."* 공개 저장소는 GitHub raw URL로 `.glb`만 게임 없이 추출 가능해 §3.5의 "extract, or access" 해석에 걸린다. 공식 문서가 공개 저장소 케이스를 명시하지 않아 **회색지대**이나, **8/3 10:00 이후 커밋 불가**라 지적받아도 되돌릴 수 없다. 이 조건에서 회색지대는 불가다.

깨끗한 대안(전부 CC0 확인): Quaternius, Kenney, CMU Mocap, cgspeed BVH, itch.io KayKit, three.js `RobotExpressive.glb`(Tomás Laulhé, CC0).
**금지**: AMASS/SMPL(명시적 상업 금지 + No Distribution), Sketchfab CC-BY 축구 클립 다수가 Mixamo 클립명 그대로 = 라이선스 세탁, three.js 번들 `Soldier.glb`/`Xbot.glb`(Mixamo 유래).

**2. 품질 델타가 회수되지 않는다.** 카메라 상수로 계산한 화면상 선수 크기:

| 샷 | 선수 픽셀 높이 | 사용 비중 |
|---|---|---|
| broadcast | **40~52 px** | 대부분의 시간 |
| highlight | 71~96 px | 슛·세이브·코너 |
| celebrate | 93~126 px | 골 후 4.5s |
| goal-cam | 131~176 px | 골 후 0.9s |

40~52px에서는 스킨드 메시와 21개 캡슐 관절체가 구분되지 않는다. 리깅이 값을 하는 건 세리머니뿐인데 그때는 선수가 뛰지 않는다.

**3. 리깅만 넣고 발 IK를 못 넣으면 오히려 나빠진다.** 클립은 보폭이 상수로 구워져 있어 미끄러짐이 불규칙 노이즈가 아니라 **주기적·체계적**으로 나타나고, 눈이 즉시 패턴을 잡는다. 발 IK는 1.5~3일이며 마감 여유가 없다.

**참고 — 드로우콜은 오히려 스킨드가 유리하다.** 현재 절차적 선수 1명 = 21 메시 → 22명 462 드로우콜. 스킨드 GLB는 22명 44~66 드로우콜. three r185는 항상 boneTexture를 써서 본 수 상한도 없다. 즉 기술적으로는 가능하며, 막는 것은 라이선스와 **IK 없는 리깅의 역효과**다.

**재검토 조건**: B-1~B-5가 끝나고 시간이 남으면, Kenney Mini Characters(CC0, 247KB/체, 32클립 내장, Blender 작업 불필요)로 **스킨드 티어를 추가**(절차적 경로를 폴백으로 유지). 단 Kenney는 조인트 7개라 **무릎·팔꿈치가 없어** 현재 4단 체인보다 관절 표현이 후퇴한다는 거래 조건을 인지할 것.

전체 조사 근거는 이 문서 작성 시점의 리서치 보고에 있으며, 핵심 파일 경로:
`player3d.ts`(`PlayerRig` 363행 / `apply()` 837행 / `createPlayer()` 599행), `movement.ts`(`actionT` 554행 / `STRIDE` 62행), `Match3D.tsx`(배선 200·327행 / 폴백 136·149·397·441행), `camera.ts` 44~71행, `scene.ts` 462~470행.

## 사용자 신규 아이디어 (2026-07-26 접수 · 평가 포함)

### N1. 경기 시작 입장 연출 + 포메이션별 선수 소개 — **채택 권고**

심판·양팀 선수가 터널에서 줄지어 입장하고, 포메이션에 따라 선수를 짧게 소개하는 연출.

**평가: Phase B에서 가장 비용 대비 효과가 큰 항목일 수 있다.** 이유:
- **필요한 부품이 전부 이미 있다** — 3D 선수 리그, 스타디움, 관중, 카메라 프리셋(`camera.ts`), 한국어 TTS, 관중 사운드, `PlayerCard`. 신규 에셋 0.
- **스크립트 시퀀스라 D1~D4의 영향을 안 받는다.** 입장은 정해진 경로를 걷는 것이라 리사주·발 미끄러짐 문제의 사각지대다. 즉 **지금 당장 만들어도 품질이 나온다.**
- **시연영상 필수 비트를 직접 채운다.** 심사 제출물의 "② 선수 배치·전술 설정" 비트에 얹을 그림이 생긴다.
- **312명 검수 데이터가 처음으로 화면에 선다.** 실명·번호·포지션을 공들여 맞춰 놨는데 지금은 작은 도트뿐이다.

**설계 요구**
- **반드시 스킵 가능해야 한다.** 심사자는 3분 안에 판단한다. [건너뛰기] 상시 노출 + 2회차부터 기본 스킵(localStorage) 권고.
- 길이 목표 **20~30초**. 그 이상이면 캠페인 8경기에서 마찰이 된다.
- 구성안: 터널 워크아웃 → 하프라인 정렬(심판 중앙) → 카메라가 홈 XI를 포메이션 순으로 훑으며 이름·번호·포지션 카드 → 주장 악수 → 킥오프.
- 국가 연주는 **넣지 않는다** — 곡 자체는 퍼블릭 도메인이어도 **녹음물에는 저작인접권**이 붙는다. 관중 앰비언스로 대체.
- 카메라는 B-6의 UEFA 규격 작업과 프리셋을 공유하므로 **B-6과 묶는 것이 효율적**이다.

**추정 1~1.5d.**

### N2. ComfyUI로 한국 선수 개개인 프로필 사진 생성 — **다른 방식을 권고**

의도(선수단이 실재감을 갖게, 개개인이 구별되게)는 정확하다. 다만 지금 형태로는 권하지 않는다.

**막는 것: 초상권.** 손흥민·김민재 등은 실존하는 식별 가능한 개인이다. AI로 실존 인물의 얼굴을 생성해 **공개 배포 URL + 공개 GitHub**에 올리는 것은 한국법상 초상권·퍼블리시티권 문제에 직접 닿는다. 그리고 이건 8/3 이후 되돌릴 수 없다(리깅 라이선스와 동일한 구조의 위험). 심사자가 알아보면 가점이 아니라 감점 요인이다.

역설도 있다. AI가 실제로 알아볼 만한 손흥민을 만들면 그게 문제 상황이고, 못 만들면 "개개인의 포인트를 살린다"는 목적이 달성되지 않는다.

**실무 비용도 크다.** ComfyUI는 로컬 실행 도구라 내가 돌릴 수 없고 사용자가 직접 해야 한다. 한국 26명 생성·선별·리터치 + 외국팀 제네릭 세트 + 번들 1MB 이상. 마감 대비 부담이 크다.

**대안 — 절차적 아바타 생성기 (권고)**
- 이미 `textures.ts`·`numberTexture()`가 캔버스 절차 텍스처를 만들고 있다. **같은 아키텍처**로 `playerId` 시드 결정론 아바타를 만든다.
- 변주 축은 **이미 가진 실제 데이터**에서: 포지션, `physical`(체격), `pace`(체형), `foot`, 등번호, 키플레이어 여부. 헤어·체격·피부톤·킷을 조합.
- 결과: 라이선스 0, 번들 0, 수작업 0, 결정론(리플레이 안전), 실존 인물 초상 아님. 26명이 서로 구별된다.
- 실재감의 핵심은 얼굴이 아니라 **카드 디자인**이다. FM도 얼굴은 제네릭이고 아무도 문제 삼지 않는다. `PlayerCard`의 육각 레이더·스탯·키플레이어 배지가 이미 그 일을 하고 있으니, 거기에 아바타를 얹는 편이 투자 대비 효과가 크다.
- N1의 선수 소개 연출과 결합하면 아바타가 실제로 쓰일 자리가 생긴다.

**추정 0.5~1d.**

사용자가 그래도 실사 프로필을 원한다면, 법적으로 깨끗한 경로는 **선수 본인/협회 허락**이거나 **라이선스된 사진 구매**뿐이다. 해커톤 일정 안에서는 현실적이지 않다.

## 부록 — Phase A 완료 시점에 남은 엔진 밸런스 문제 3건 (미수정)

Task 5b 후속 보정(`f5bfa55`) 중 계측으로 발견. 추천 계층이 아니라 **엔진 밸런스** 문제이며,
Task 2가 라인·압박에서 제거한 것과 **같은 종류의 단조 지배**다. 밸런스 게이트 9개는
라인·압박·템포만 검사하므로 아래 축들을 잡지 못한다.

### E1. `very-attacking` 멘탈리티가 지배적 (가장 심각)

n=600 실측에서 `trap > 0`인 상대 **10팀 전부**에 대해 `very-attacking`이 `attacking`을
승률·승점 양쪽에서 이긴다. `MENTALITY_FX['very-attacking']`의 `counterVulnerability: 1.28`이
실제 실점으로 거의 나타나지 않는다(arg 기준 1.97 → 2.09).

**즉 멘탈리티 5단은 11경기 중 10경기에서 정답이 하나다.** Task 2 이전의 라인·압박과 동일한 상태.

처방 방향: `counterVulnerability`가 실점에 실제로 닿게 하거나(현재 `chanceP`에만 곱해져
전력비·suppression에 희석됨), 공격적 멘탈리티에 체력 소모·파울 비용을 부여.

### E2. 라인 높이에 내부 최적점이 없다

`trap > 0`인 모든 상대에서 압박 ≤ 68이면 라인 100까지 단조 증가한다. `lineVul`의 비용이
`compress`의 이득을 0~100 구간 안에서 한 번도 추월하지 못한다. 기울기는 trap에 비례:
`trap 0.58 → +3.7pp / 0.65 → +5.5 / 0.92 → +7.7 / 1.10 → +8.8`.

밸런스 게이트는 통과한다 — 게이트가 요구하는 건 "최적 방향이 상대에 따라 뒤집힐 것"이고
그건 성립하기 때문이다(esp는 반대). 다만 **한 경기 안에서는 여전히 정답이 하나**다.

`recommendPlan`은 이걸 알면서도 일부러 trap 비례값을 권하고 항상 100을 권하지 않는다
(상대별 차별화 유지 + "무조건 최대"는 조언이 아니므로). 상대당 1~3pp를 남겨두는 선택이다.

### E3. `groupIntensity`의 존별 부호가 어긋난다

`attack: +1`은 체력 −4%에 **+3~5pp** — 사실상 공짜다.
반면 `midfield: +1`은 **음수**(arg −3.6pp, mar −3.8pp).

같은 구조의 배수(`groupIntensityZoneFactor`가 존 무관하게 +1 → 1.06)인데 부호가 갈리는 것은
의도된 설계로 보기 어렵다. `zoneStrength`의 midfield가 점유 판정(`possW`)에만 쓰이고,
점유는 참여 빈도 정규화 때문에 승패에 거의 중립이라는 Task 2의 관찰과 연결될 가능성이 높다.

**착수 조건**: Phase B의 B-1~B-4보다 우선순위가 낮다. 다만 E1은 "전술 선택이 게임이 되게 한다"는
Phase A의 목표를 멘탈리티 축에서 되돌리고 있으므로, 시간이 나면 E1 → E3 순으로 볼 것.
착수 시 `runAxisSweep`을 멘탈리티·그룹 적극성 축으로 확장해 게이트를 먼저 세워야 한다
(Task 1~2에서 검증된 순서).

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A** | 스크립트는 **이벤트·스코어만** 유지하고, 체력·스탯·점유 흐름은 전반에도 시뮬 | 기획서 훅 유지, 변경 최소, 22' 개입이 의미를 가짐 | 플랜이 좋아도 스코어는 역사 고정 — 위화감이 완전히 사라지진 않음 |

권고: **C > A > B.** 1차전은 "실제 역사 2-1 재현"으로 훅을 보여주고, 2·3차전부터 감독의 플랜이 90분 전체를 지배하게 한다. 사용자가 원래 원했던 "내 개입이 결과를 바꾼다"에 가장 가깝다.

### F2. 코치 조언이 항상 3종 등장하고 시점을 모른다

`src/game/coach.ts:74` `buildCoachAdvice` — 함수 주석이 정직하게 밝히듯 **"항상 수비/공격/피지컬 3인"**이 무조건 push되고, 세트피스만 조건부(코너 ≥ 4)다.

- **임계값이 없다.** `bottom3Stamina`(`coach.ts:61`)는 값과 무관하게 하위 3명을 반환한다 → 체력 100에서도 "체력 최하위 3인: 김문환 100, 김민재 100, 김승규 100. 압박을 유지하면 후반 급락이 예상됩니다."
- **시점을 모른다.** `minute`을 읽지만 `hash(minute:score)`로 공격 패턴을 고르는 데만 쓴다. 전반/후반·잔여 시간·교체 카드 수·경고 누적에 따른 분기가 없다.
- **0 데이터에서 문장이 무너진다.** `fewer = own.xg < opp.xg`가 `0 < 0 = false` → "상대(xG 0.00)보다 찬스가 **많습니다**".
- 제안 문구가 상수라 매번 동일하게 읽힌다.

F1을 고쳐도 F2는 남는다. **둘 다 고쳐야 22' 개입이 의미를 갖는다.**

**★ 사용자 확정 (2026-07-26): 조언할 게 없는 코치는 등장하지 않는다.**
> "전반에 2명 코치만 조언하고, 후반에는 조언할 게 많은 4명이 조언해도 된다는 거야.
>  꼭 3명이 없는 근거 억지로 만들면서 조언할 필요 없어."

즉 코치 수는 **0~4명 가변**이다. 근거가 데이터에서 나오지 않으면 침묵한다.
전원 침묵도 허용 — 그때는 "코치진: 특별히 드릴 말씀 없습니다" 한 줄이면 충분하다.
이 규칙이 F2 처방의 최상위 제약이며, 아래 발동 조건은 전부 여기서 파생된다.

처방 방향:
- 각 코치에 **발동 조건**을 준다(피지컬은 최저 체력 ≤ 75 또는 60분 이후, 수비는 상대 유효슛 ≥ 2 등). 조건 미충족이면 등장하지 않는다 — 3장이 늘 뜨는 것보다 1장이 뜰 때 무게가 있다. 등장 수는 0~4로 가변.
- **국면 축**을 넣는다: 전반 초반(~25') / 전반 종료 전 / 하프타임 / 후반 중반 / 종반(75'+). 국면별 문구·제안 풀을 분리.
- 데이터가 비었을 때 전용 문구("아직 표본이 적습니다 — 상대 전개를 지켜보시죠").
- 스코어·잔여 시간·교체 잔여 카드를 제안에 반영.

### F4. 워룸에 경기 스탯이 없다 (신규 요구)

### F5. 선수 개인 경기 스탯 (신규 요구)

교체 판단 근거로 개인 기록이 필요하다. **엔진 변경 없이 `MatchEvent`에서 파생 가능한 것**:
슛 수(`shot`/`miss`/`goal` + 그 선수가 대상인 `save`), 골, 어시스트(`assistId`), 파울, 경고.
**엔진 변경이 필요한 것**: 패스 성공률·터치 수·주행거리 — 현재 개인 단위로 추적하지 않는다. F1의 A/C안으로 전반을 시뮬하게 되면 분당 개인 기여를 쌓을 자리가 생긴다.

권고: 1차로 **이벤트 파생 5종만** 붙이고(비용 낮음), 패스/터치는 F1 처리와 묶어서 판단.
